## 1. コンセプト

- **何か**: 直感的に家計簿をつけられる iPhone アプリ。名前は SaifuLog（サイフログ）。
- **入力**: チャットのように「ランチ 850」と一行送るだけで記録する。記録はタイムラインに
  吹き出しで並ぶ。記録も質問も同じ入力欄から行う。
- **売り**: お金のデータを外に出さない。AI も含めて端末内で完結し、開発者のサーバーを持たず、
  家計のデータを端末の外へ送らない（利用者が有効にした iCloud を除く。§5-3）。そのため API 費用も
  かからない。
- **続けやすさ**: 家計簿は入力が面倒になるとやめてしまいやすい。入力を一行にし、分類と
  計算はアプリが引き受ける。

## 2. 入力の設計（ひとこと入力）

検討した案のうち、**案B「ひとこと入力」** と、それを iOS の AI で広げる **案B+** を採用した。

- 入力欄はホームの下に 1 つだけ置く。カメラ・マイク・送信のボタンを並べる。
- 送った一行は吹き出しとしてタイムラインに出し、すぐ「直す」「取り消す」を示す。
  読み違いをその場で直せれば、AI の精度が完璧でなくても使えるため。
  - 試作済み。記録の直後のバナーに「直す」「取り消す」を並べる。「直す」は ⑥ のシートを開く（1 回の送信で
    複数件を記録したときは、どれを直すかをメニューで選ぶ）。取り消すと送った文を入力欄に戻し、書き直して
    送り直せるようにする。1 回の送信で複数件を記録したときの「取り消す」は、その全件を消し、送った文を 1 回だけ戻し、
    VoiceOver には消した全件を読み上げる。VoiceOver やスイッチコントロールを使っているときは、バナーを時間で引っ込めない
    （たどり着く前に消えるため）。保存の失敗のアラートを出している間も、時間では引っ込めない（閉じたら数え直す）。
  - **次の文を送ったら、前の記録の「取り消す」はすぐに引っ込める**（バナーも VoiceOver の操作も。読み取りの間も出さない）。
    読み取りの間も前の記録を指したまま押せると、前の記録が消えて前の文が入力欄に戻り、いま送った文の記録だけが残るため
    （送った文が読めなかったときも、戻るのはその文になる）。前の記録は、吹き出しから直す・長押しで消すことができる。
  - 記録の直後でなくても、吹き出しを押せば ⑥ で直せる（§9）。
- **記録はいつでも削除できる。** 吹き出しの長押し（コンテキストメニュー）の「削除」か、⑥ の「この記録を削除」から、
  確認のダイアログを挟んで消す。VoiceOver からは操作の一覧（アクション）の「削除」で同じことができる。
  「取り消す」は直後にしか出ないので、それを逃した誤りを消す手段が要るため。確認を挟むのは、
  削除は元に戻せないため。
- 質問（「今月カフェいくら?」）も同じ入力欄に打つ。記録か質問かはアプリが見分ける。
  入口を分けると、利用者が「どこに書けばいいか」を考えることになるため。
  - 試作済み。見分けはコア（`InputIntentClassifier`）がコードで決め、**誤って記録にならないことを優先する**（§9 の家計への質問の決め事）。

## 3. 端末内 AI の使い方

AI はすべて Apple の Foundation Models フレームワークで、端末内で動かす。

### 3-1. AI をどこで動かすか

| 観点 | 端末内 AI（Foundation Models） | クラウドの LLM API | ルールベースのみ |
|---|---|---|---|
| データが外に出ない | ◎ | ✕ | ◎ |
| 運用の費用 | ◎ かからない | ✕ 使うほどかかる | ◎ かからない |
| 通信なしで動く | ◎ | ✕ | ◎ |
| 自然な文章の理解 | ○ | ◎ | △ |
| 対応機種の広さ | △ Apple Intelligence 対応機種のみ | ◎ | ◎ |

クラウドは理解力で勝るが、「データを外に出さない」という売りと両立せず、サーバーと
従量の費用も要る。**端末内 AI を主にし、ルールベースを下支えにする**（§4）。

### 3-2. 文章を理解して記録する（ガイド付き生成）

`@Generable` の型を決め、モデルにはその形で値を返させる。自由文を返させて後から
読み解くより、壊れた出力が来にくいため。

| 入力 | 記録のされ方 |
|---|---|
| ランチ 850 | 食費 ¥850 |
| 昨日 焼肉12000 4人で割り勘 | 前日・食費・¥3,000（立て替えた ¥9,000 はメモ） |
| スーパー2480とドラッグ1200 | 2 件に分けて記録 |
| 給料 25万 | 収入 ¥250,000 |
| 4人で割り勘 1人あたり3000円 | ¥3,000（1 人分として書いた額は割らない） |
| 返金 -500 | 収入 ¥500（返金） |

- **件の分け方はコード（SaifuLogCore の `EntryInput`）で決め、モデルには区間ごとに 1 件だけ
  生成させる。** 記録の配列を返させると、1 件の入力にも空の要素や入力に無い金額の要素が混ざったり、
  同じ記録を繰り返したりする（実機で 1 件の入力に要素がちょうど 1 つ返ることがほぼ無かった）。
  単体の型で 1 件ずつ生成させると正しく返る。区間ごとに新しいセッションにして、前の件を引きずらせない。
- 割り勘の例では、モデルには金額の表記（割る前の総額「12000」）だけを取り出させ、人数は尋ねない。
  人数は入力のその件にかかる「割り勘」の語と「N人」からコードが決め、**¥3,000 と ¥9,000 も
  コードで計算する**。端末内モデルは小さく、割り算を任せると間違えることがあるため。
- 金額と日付は、モデルには書かれた表記のまま抜き出させる。「25万」「1万2千500」のような単位、全角数字、
  「昨日」「おととい」「9/26」のような日付の言い回しの換算はコード（SaifuLogCore）で行う。
- **指示文と `@Guide` の説明には、具体的な数字や単位の例を書かない。** モデルが説明の数字や単位を、
  入力に無くても写して返すため（「ドラッグ1200」に「1200万」が返った）。
- モデルが返した値は、すべてコアで入力と突き合わせてから使う（§4-3）。
- **自信がないときだけ聞き返す。** 毎回確認を挟むと一行入力の軽さが失われるため。
- **利用者の修正を覚える。** 「この言葉はこのカテゴリ」という対応を端末内に残し、次から
  AI への手がかりと、ルールベースの辞書の両方に使う。

### 3-3. レシート・スクショから明細ごとに仕分ける

- iOS 27 で加わった画像入力と、文字認識（OCR）を行うツールを組み合わせ、明細ごとに
  カテゴリを分ける。
- 読み取り結果はホームのタイムライン内にカードとして出し、確認してから確定する。
- 明細の合計とレシートの合計額はコードで突き合わせる（案）。合わないときはカードに印を出す。

### 3-4. 家計に質問する（ツール呼び出し）

試作済み（`SaifuLog/AI/FoundationModelsQuestionAnswerer.swift`。数字と照合はコア）。

- **ツールは 1 つ（`queryLedger`）で、引数は `@Generable` の列挙（期間・知りたいこと・カテゴリ）だけ。** 自由な数は受け取らない。
  期間の選択肢は今日・昨日・今週・先週・今月・先月・今年・直近の日数、知りたいことは支出の合計・収入の合計・収支・カテゴリ別の内訳・
  あるカテゴリの支出・件数・予算の残り・1 日あたりに使える額・いちばん使ったカテゴリ、カテゴリは 8 種と「指定なし」。
  直近 N 日の N もモデルに選ばせず、文からコードが読む（割り勘の人数と同じ考え方）。
- **数字はツールの中でコア（`LedgerQuestionAnswerer`）が計算する。** 期間は `ReportPeriod`、集計は `LedgerSummary`、内訳は
  `CategoryBreakdown`、予算は `BudgetStatus` で、ホームの帯と月のまとめの数字と食い違わない。ツールはモデルに結果の文
  （`LedgerAnswerFacts`。期間・知りたいこと・結果・元になった件数）を返し、同じ答えを画面のために残す。
- **文からコードが読めたもの（期間の言葉・直近 N 日・カテゴリの名前・はっきりした指標の語）は、モデルの選択より優先する**
  （`QuestionReading.resolved(with:)`）。モデルの選択を使うのは、辞書に無い言い回し（「年初から」「外で食べた」）のときだけ。
  指標の語が無く「いくら」「合計」だけの文では、モデルが件数・いちばん使ったカテゴリ・内訳を選んでも支出の合計（カテゴリが
  あればそのカテゴリの支出）で答え、文にカテゴリがあれば予算・収入・収支の選択もそのカテゴリの支出にする（金額を聞かれて件数を
  答えたり、文に書かれたカテゴリを落としたりしないため。「今月カフェいくら?」の答えは AI の有無で変わらない）。カテゴリの無い
  文の予算・収入・収支の選択はそのまま使う（辞書に無い言い回しをモデルが読めることがあるため）。
  「去年」「9/26」のような答えられない書き方を含む質問は、モデルに渡さずに読めない質問にする（聞かれていない期間の数字を出さないため）。
- **モデルには一言の要約文だけを書かせ、回答カードにはツールが計算した数字をそのまま、一言とは別に出す。** AI が言い回しの中で
  数字を書き換えても、正しい値が見えるようにするため。
- **一言にツールの結果に無い数字があれば、一言を捨てて定型文にする**（`AnswerSentenceCheck`。コアに置いて `swift test` で確かめる）。
  数字は記録の読み取りと同じ読み方（半角・全角・桁区切り・「25万」）で読み、**前後の語で種類に分けて、結果の同じ種類の数字とだけ比べる**。
  「¥」「円」付きは金額、「件」「回」付きは件数、「日」付きは日数（「残り3日」「1日あたり」）、「%」付きは割合、日付の数字は日付の形
  （「2026年」「9月」「9月30日」「9/30」）のときだけ結果の期間の日付と比べる。種類の無い数字は結果の金額・件数・日数・割合と比べ、
  日付の数字とは比べない（期間の「9月1日から9月30日まで」の数字で、「30件」「9件」のような作り話が通らないように）。結果に無い
  数え方（「人」「割」「週」「か月」など）の数字も捨てる。漢数字も、位を含むか数える語（円・件・日など）が続けば数として比べる。
  小数の割合や桁の多すぎる数字は確かめられないので捨てる。**収支の向きも比べる**。黒字なのに「赤字」「マイナス」「-¥3,000」
  「支出が収入より多い」と書いた一言は、数字が合っていても捨てる（結果の文の「+」「-」と「収入が支出より多い」などの注記に無い向き
  は使わない）。収支ではない答えに向きを書いた一言も捨てる。
- モデルがツールを呼ばずに答えたら、数字の根拠が無いので使わず、キーワード辞書（`QuestionParser`）で答え直す。生成の失敗も同じ。
- 指示文と `@Guide` には具体的な数字や単位の例を書かない（§3-2 と同じ。アプリのテストで指示文とツールの説明を確かめている）。

### 3-5. 週のふりかえり

- 1 週間の数字はコードで集計し、AI は短いメッセージにするだけ。
- 無料は簡易版。プレミアムには月の AI レポートと予算の提案がある（§6）。

### 3-6. 後の段階

- 声で記録する（Speech）。
- Siri・ショートカット・アクションボタンから記録する（App Intents）。

## 4. AI の制約とフォールバック

### 4-1. 使えない場面

- **Apple Intelligence 対応機種のみ**（iPhone 15 Pro 以降など）。
- 対応機種でも、Apple Intelligence がオフのときや、モデルのダウンロード中は使えない。
  `SystemLanguageModel.default.availability` で判定する。
- 生成そのものが失敗することもある（安全のための拒否、文脈の長さの超過など）。

### 4-2. 切り替え方

AI が使えないとき、または失敗したときは、**SaifuLogCore のキーワード辞書によるルールベース
解析に切り替える。** AI が無くても記録できるアプリにする。AI は上乗せであって前提ではない。

| 機能 | AI が使える | AI が使えない |
|---|---|---|
| ひとこと入力 | 文章を理解（品目・カテゴリ・収入かの言い回し）。件の分け方・日付・割り勘・金額の換算は、AI が使えないときと同じくコードが決める | キーワード辞書で金額・カテゴリ・日付・収入・割り勘（割り勘の語と「N人」があるとき）・区切りのある複数件を読む（§4-4）。言い回しが崩れた文には弱い |
| レシート・スクショ | 画像入力 + 文字認識で明細ごとに仕分け | 未決（§13） |
| 家計に質問 | ツール呼び出しで質問を読み、一言を添える（数字はコード） | キーワード辞書（`QuestionParser`）で期間・指標・カテゴリを読んで答える（一言は添えない）。読めなければ質問の例を出す |
| 週のふりかえり | AI が言い回しを作る | 定型文に数字を差し込む（案） |

### 4-3. 読み違いへの備え

- **計算はさせない。** AI は値を取り出すだけ（§3-2）。
- AI の結果は、SaifuLogCore の `ExtractedEntry.resolveAll` で入力の区間と 1 件ずつ突き合わせる。
  入力に無い値で、保存する金額・日付・種別が変わらないようにするため。照合をコアに置くのは、
  端末に依存しない `swift test` で確かめられるようにするため。
  - **件数と金額:** 返った件数が区間の数と合わないとき、または金額がその区間に書かれた額のどれとも
    合わないときは、AI の結果をすべて捨ててルールベースで読み直す。区間どうしの金額は重ならないので、
    入力の金額を二重に使うことも、使い残すこともない。将来は、記録せずに聞き返す形にしてもよい（案）
  - **日付:** 表記が指す日が、区間に書かれた日付かその件に割り当てた日付と合うときだけ使う。
    合わなければ入力から読んだ日付を使う
  - **割り勘の人数:** モデルには尋ねない。入力のその件にかかる割り勘の語と「N人」の組から決める
    （ルールベースと同じく、人数だけでは割らない。1 人分として書いた額は割らない）
  - **収入:** モデルが収入と返しても、区間に打ち消しの語（「収入印紙」）か、後ろに支出の語が続く
    収入の語（「入金手数料」）があれば支出にする。収入の語が無いだけなら収入のまま
    （「お小遣いもらった」は AI のほうが読める）。マイナスを付けた額はいつでも収入（返金）。
    正の金額の後ろの値引きの額（「850(-100引き)」の 100）は金額として突き合わせない（ルールベースで読み直す）。
    主な金額に添えた額（税抜きの値段・マイナスを付けない値引き・合計・おつり・ポイント。§4-4）も突き合わせない。
    マイナスを付けない値引きのある件で、値引きの前の額（「850 100円引き」の 850）が返ったら、ルールベースと同じく引いた額で記録する
  - **品目とカテゴリ:** 品目そのものがルールベースのメモ（その件の金額・日付・割り勘の語を除いた区間）に
    含まれていれば、そのまま使う（「セブン11」「100円ショップ」の数字を抜かない）。そうでなければ金額・日付・
    人数を除いた品目を見て、区間に書かれた言葉でなければ（「昨日」だけ、作った品目）、ルールベースのメモと
    カテゴリに置き換える。根拠の無い「食費」を保存しないため
- 記録の直後に「直す」「取り消す」を必ず出す（試作済み。§2）。直した内容を覚えるのはまだ（§3-2・§5-2 の覚えた修正）。
  記録は長押しでいつでも削除できる（§2）。

### 4-4. 読める書き方（ルールベースと AI で共通）

件の分け方・日付・割り勘・金額の換算はコードで決めるので、AI が使えるかどうかで変わらない。
辞書の詳細は SaifuLogCore の `EntryScan` と `RuleBasedParser` が正で、テストに例がある。

| | 読めるもの | 決めたこと |
|---|---|---|
| 金額 | 半角・全角の数字、桁区切り（日本語の入力の「、」も。「1、280円」）、「円」「¥」（空白を挟んでもよい）、「25万」「1万2千500」「5百」「1億2000万」、「500×3」「3x500円」「2個×300」 | 区間の最後の金額を採る（1 人分として書いた額があればそれを、税込みの額があればそれを採る。主な金額に添えた額は下の「添えた額」）。「、」は前後が数字で後ろがちょうど 3 桁のうえ、数の先頭の組が 1〜2 桁（「1、280」「12、800」）か後ろの組が「000」（「128、000」）のときだけ桁区切りとして読む。「、」は件の区切りにも使うので、「ランチ850、400」「850、100円引き」のように 3 桁の金額を並べた「、」は区切りのまま（¥850,400 のような金額を黙って記録しないため）。日付の日・時刻の分・小数の後ろの桁に続く「、」「,」（「9/26、850円」「12:30、400円」）も桁区切りにしない（数の先頭の組ではなく、取り除くと ¥26,850 や ¥30,400 のような金額を黙って記録するため）。「。」は小数点として読まない（「8。5万」は区切り）。掛け算は、どちらかが 1〜999 の個数のときだけ掛けた額の 1 件にする。記号に続けて書いた「×2」「x2」は、ほかに金額があれば個数とみなす（「コーヒー×2 800」）。時刻（「12:30」）、電話番号、0 で始まる 2 桁以上の数字、位も円も付かない小数、人数や数量の幅（「3-4人」の 3）は金額にしない |
| 日付 | 「今日」「昨日」「一昨日」「おととい」「3日前」、「9/26」「9-26」「9.26」「9月26日」、「26日」、「2025/9/26」「25/9/26」「2025年9月26日」「令和7年9月26日」「R7/9/26」 | 「今日」「9/26」は、送った瞬間の日時を基準に読み、保存する日時（記録した日時・使った日時）にも同じ値を使う（AI の読み取りを待つ間に日付が変わっても、読んだ日付と保存する日付がずれないように）。1 回の送信の複数件は、書いた順に並ぶよう記録した日時を 1 ミリ秒ずつずらすが、ずらした日時が送った日の終わりを越えるときは、起点を前へ寄せて同じ日の中に収める（月末の 23:59:59.9995 に送った 3 件が、翌月の記録にならないように）。年を省いた月日は、今日から 60 日先までは未来の日付（年末に書いた「1/5」は来年）、それより先は去年とみなす。払う予定の家賃のように少し先の日付で書くことがあるため。年を書いた日付は、未来でもその年のまま。「26日」（1〜31 に「日」、直後が「前・間・分・目・後」でない）は今月のその日。「2泊3日」「1日1回」は日付にしない。「-」「.」でつないだ月日は、英字や「.」に続くもの（「ver1.2」「PS5-2」）と、人数や数量が続くもの（「3-4人」）は日付にしない。「.」は日を 2 桁で書いたとき（「9.26」「10.05」）だけ日付にする（「1.5」「10.5」は小数として書くことが多く、黙って何か月も前の日付になるため）。成り立たない日付（「9/31」、9 月の「31日」、2026 年の「2月29日」）は金額にせず、メモに残す（今日の記録になるので、読めなかったことに気づけるように）。暦はグレゴリオ暦で数える（和暦・仏暦の設定でも「2026」は西暦） |
| 割り勘 | 「割り勘」の語と「N人」（2〜100 人）の組 | 割り勘の語にいちばん近い人数を採る（「友達3人と焼肉 12000 4人で割り勘」は 4 人）。「1人あたり」「1人分」「一人」などを直前に付けた額は 1 人分として割らない。そのときは、ほかの金額（総額）と割り勘の語をメモから除き、「焼肉（4人で割り勘・1人分）」のように書き足す。総額と 1 人分の額は、どちらを先に書いても 1 件にする（「12000 焼肉 4人で割り勘 1人3000」を 2 件にすると、同じ支出を 2 度記録するため） |
| 収入 | 「給料」「賞与」「ボーナス」「バイト代」「時給」「日給」「手取り」「入金」「還付」など。「お年玉」「お小遣い」「仕送り」「お祝い」は「もらった」などと組のときだけ | 「給料日」「収入印紙」「国民年金」のような打ち消しの語や、収入の語の後ろに支出の語（手数料・保険・経費・天引き・返済・税金など）が続く言い回しは支出。前にある支出の語は見ない（「所得税の還付」は収入）。「給料日」は、後ろに「入った」などの受け取った語が続くときと、ほかに語が無いとき（「給料日 25万」）は給料の記録とみなして打ち消さない（「給料日なので焼肉」は支出） |
| 返金 | 「返金 -500」「−500」のようにマイナスを付けた額（全角の「－」、ハイフン「‐」、ダッシュ「–」「—」「―」も「-」として読む） | 返金として収入（カテゴリはその他）に記録する。メモに記号は残さない。記録は支出と収入の 2 種別で、金額はどちらも正の整数で持つため（§5-2）。同じ件で正の金額の後ろに置いたマイナスの額（「ランチ 850(-100引き)」「ランチ 1000 -200」）は値引きの説明とみなし、返金にもその件の金額にもしない（正の金額で記録し、値引きはメモに残す） |
| 複数件 | 金額の後ろの「と」「、」「。」「/」・改行（CRLF・CR も）や空白での区切り、金額を先に書く並び（「850 ランチ 400 コーヒー」） | 金額の後ろの空白は、次に語が続くか、数字で書いた日付・時刻から次の件が始まるとき（「9/26 ランチ 850 9/27 カフェ 400」「ランチ 850 12:30 カフェ 400」）に区切る。語で書いた日付（「昨日」）と同じ扱いにする（区切らないと前の金額が消えて 1 件になるため）。金額の後ろに空白を挟んで人数・数量・割り勘の句（「4人で割り勘」「2本」「割り勘 4人」）を書いたときは、句を前の件に残し、句の後ろの空白（か独立した「と」）から次の件にする（「焼肉12000 4人で割り勘 ランチ 850」は ¥3,000 と ¥850。句を後ろの件に付けると、割り勘が後ろの件の金額にかかるため）。後ろが数字や 1 人分の額なら区切らない（「ビール 500 2本」「焼肉 12000 4人で割り勘 1人3000」は 1 件）。区切りの無い続け書きは、次の品目がカタカナ 1 語で、その直後に空白を挟まず金額が続くとき（「スーパー2480ドラッグ1200」）だけ分ける。漢字やひらがなの品目（「ランチ850弁当500」）や、語の後ろに空白を置いたもの（「ドラクエ12ソフト 8000」「コーラ500ペットボトル 160」）は 1 件のまま読む。「500円引き」「109で服」や型番・容量の数字を誤って分けないため。金額を先に書く並びとみなすのは、最後の金額の後ろにも語があるときだけ（「109で服 5000」は ¥5,000 の 1 件） |

| 件ごとの日付と割り勘 | 「昨日 焼肉12000 4人で割り勘、今日 ランチ 850」 | 文（「、」「。」「/」などの強い区切りで分かれるまとまり）ごとに割り当てる。日付は その件 → 同じ文の後ろ → 前の件から引き継ぐ → 最後に単独で置いた日付 の順。割り勘は その件 → 同じ文の中 → 最後に単独で置いた割り勘（「…、4人で割り勘」）の順で、前の件からは引き継がない |

**対応しない表記**（どちらの経路でも読まない。読めた部分だけで記録するので、記録の直後の「直す」で直してもらう）:

- 「明日」「明後日」「昨夜」「先週」「金曜」「先週の土曜」のような、「今日」「昨日」「一昨日」「おととい」「N日前」以外の
  相対の日付と曜日（日付にせず今日の記録になり、語はメモに残る）
- 漢数字だけの金額（「千円」「一万円」「千五百円」。数字が無いので「金額が無い」になる）。「1万2千」のように数字と
  位を組み合わせたものは読む
- 「÷」での割り勘（「焼肉 12000÷4」は「÷」の後ろの 4 を金額として読む）。割り勘は「割り勘」の語と「N人」で書く
- 品目に付けた分数（「キャベツ1/2 98」「スイカ 1/8 398」は「1/2」を日付（1 月 2 日）として読む）
- 「7-11」のような、数字を「-」でつないだ店名（9-26 と同じく日付として読む）。「セブン11」のように書けば品目のまま
- マイナスを付けない返金（「返金 500」は支出として記録する。返金は「返金 -500」のようにマイナスを付けて書く）
- 先頭の組が 3 桁で、後ろの組が「000」でない「、」の桁区切り（「128、500円」は ¥128 と ¥500 の 2 件になる）。
  「、」は件の区切りにも使うため。「128,500円」とカンマで書けば 1 件で読む

日付の直後の「の」「は」「も」「に」（「昨日の飲み会」「今日もランチ」）は日付と一緒に使い終え、メモに残さない。
ただし次がひらがなのときは語の頭のことがある（「昨日のり」「今日はちみつ」「昨日もやし」）。「お」「ご」が続けば
助詞とみなし（「昨日のお茶」）、「の」「は」は続くひらがなが 1 文字だけか、知っている語（「はちみつ」など）のときに
語の頭として残す。「も」「に」はひらがなが続けば語の頭として残す。

数字の計算がすべてコアにあれば、「AI に計算させない」をテストで守れる。

- **集計は `LedgerSummary` に集める。** 期間（`DateInterval`）の支出・収入・差額と、支出のカテゴリ別の合計を出す。
  ホームの今月の合計（`MonthlySummary`）はその薄い包み。月のまとめ・質問・週のふりかえりも同じ計算を使い、
  画面の数字と AI に渡す数字を食い違わせない。収入はカテゴリ別の合計に数えない（支出とは別の種別のため）。

  地域と iOS の設定で変わる）に従う。
  - **今日〜今年の相対的な期間は、渡された暦（利用者が iOS で選んだ暦）のまま区切る。** ホームの「今月」
    （`MonthlySummary`・`Entry.monthDescriptor`）も `ReportPeriod.thisMonth` で区切り、同じ期間にする。
    西暦に置き換えてから区切ると、イスラム暦・ヘブライ暦・ペルシア暦・中国暦のように月の区切りが西暦と違う暦で、
    まとめや質問の「今月」がホームの「今月」と別の期間になるため（和暦・仏暦は月の区切りが西暦と同じで、
    元号が変わった年も年の区切りは 1 月 1 日のまま）。
  - **西暦で読むのは、年と月を数で指す `month(year:month:)` だけ**（入力の日付と同じ方針）。和暦の暦に西暦の年を
    そのまま渡すと、令和 2026 年（西暦 4044 年）になるため。区切りも西暦の月にする（西暦の年月を指したものなので、
    月の区切りが西暦と違う暦では、`thisMonth` とは別の期間になる）。
- **予算の計算は `BudgetPlan` と `BudgetStatus` に集める。** `BudgetPlan.resolve` が保存された予算の行から有効な予算を
  決め（§5-2）、`BudgetStatus` が今月の残り・1 日あたりの額・残りの日数・超えた額を出す（決め事は §6-1）。ホームの帯と
  月のまとめと質問の答えが同じ計算を使う（画面の数字と AI に渡す数字を食い違わせないため）。
- **月のまとめの数字は `MonthlyReport` に、カテゴリ別の内訳は `CategoryBreakdown` に集める。** `MonthlyReport` は
  `ReportPeriod`（月の区切り）・`LedgerSummary`（合計）・`BudgetStatus`（予算の進み）を組み合わせ、その月の支出・収入・収支、
  1 日あたりの平均、前の月との差、日割りの目安を出す。`CategoryBreakdown` は割合を最大剰余法で整数の % に丸め、合計を
  ちょうど 100 にする（決め事は §9 の ⑦）。質問の答え（カテゴリ別の内訳・いちばん使ったカテゴリ）も同じ数字を使い、あとで作る月の AI レポートも使う。
- **CSV の書き出しの中身は `LedgerCSVWriter` に集める**（決め事は §9 の ⑧）。書き出す期間の区切りは `ReportPeriod`、範囲の境目は
  `LedgerSummary` と同じ（始まりは含み、終わりは含まない）にして、まとめの数字と CSV の行を食い違わせない。

画面の状態と操作（送信・取り消し・削除など）は、画面ごとの `@Observable` のモデル（`SaifuLog/Views/HomeModel.swift`）に
置き、画面は表示と、環境（文字の大きさ・支援技術・前面かどうか）に合わせた出し方だけを受け持つ。解析器・時計・
VoiceOver の読み上げをモデルの外から渡せるようにして、アプリのテストでメモリの上の保存先と組み合わせて確かめる。

アプリのテスト（`SaifuLogTests`）はシミュレータで動かす。`make test`（コアの `swift test`）とは別に、
`make build-tests`（`xcodebuild build-for-testing`。汎用のシミュレータ向けにコンパイルだけ）と
`make test-app`（シミュレータで動かす）で回し、CI（build.yml）も同じ 2 つを通す。`make build` はスキームの
build アクション（アプリだけ）なので、これが無いとテストのターゲットが壊れても気づけない。
シミュレータの機種は決め打ちせず、入っているもののうち、いちばん新しい iOS の iPhone を
`scripts/pick-simulator.sh` が選ぶ（ランナーのイメージが変わっても、機種が無くて落ちないように）。
購入のテスト（`StoreKitPurchaseTests`）だけは `make test-app` から除き、`make test-storekit` で SKTestSession が動く版
（`STOREKIT_TEST_OS`。いまは iOS 26.2）のシミュレータで動かす（§9 の ⑨ の決め事）。

### 5-2. データモデル（案）

実装時に確定する。ここでは形の見当だけを書く。

| モデル | 主な項目 | 備考 |
|---|---|---|
| 記録 | 日付、金額、種別（支出・収入）、カテゴリ、メモ、入力元（ひとこと・レシート・声）、元の入力文 | 元の入力文を残すと、直すときや解析の見直しに使える |
| 予算 | 対象（全体かカテゴリ）、金額、書き込んだ日時 | 月ごとには持たず、毎月同じ額を使う（§6-1）。試作済み |
| 覚えた修正 | 言葉、カテゴリ | AI への手がかりと辞書の両方に使う |

- **金額は整数（円）で持つ。** 浮動小数点の誤差を家計簿に持ち込まないため。支出も収入も
  正の数で持ち、種別（支出・収入）で分ける。円以外に広げるなら、最小単位の整数と通貨コードを
  持つ形にする（§13）。
- 記録のモデルは試作済み（`SaifuLog/Models/Entry.swift`）。予算のモデルも試作済み（`SaifuLog/Models/Budget.swift`）。
  覚えた修正のモデルはまだ。
- **記録を直すときは、直した項目だけを書き換える**（`EntryEdits.apply`）。元の入力文・入力元・記録した日時は直さない
  （元の入力文は読み違いの見直しに残し、記録した日時を変えるとタイムラインの並び（送った順）が変わるため）。
  割り勘の人数と総額は記録に持たないので、直すシートでは直せない（§13）。
- **書き込めなかった変更は巻き戻す**（`EntryStore`・`BudgetStore` の commit）。ただし SwiftData の rollback は、読み込み済みの
  モデルの値を直した値のまま残す（保存先から読み直すと戻る。シミュレータの iOS 26.4 で確かめた）。記録を直して保存に
  失敗したときは、巻き戻したあとにその記録を読み直して、吹き出しに保存していない値が出続けないようにする（アプリのテストで守る）。
- **予算は 1 行に 1 つの対象（全体 "total" かカテゴリの rawValue）と金額を持つ。** 予算をなくすときも行は消さず、
  金額 0（設定なし）を書く。CloudKit では削除が他の端末に伝わるのが遅れたり、同時に書いた値と食い違ったりするので、
  「最後に書いた値」が勝つ形にしておくため。一意制約を付けられない（CloudKit と両立しない）ので、同期すると同じ対象の
  行が重なることがある。読むときは `BudgetPlan.resolve` が対象ごとに書き込んだ日時の新しい行を採り（同じ日時なら
  額の大きい行。読み込む順番で決めると端末ごとに違う予算になるため）、書き込むとき（`BudgetStore`）は同じ行を残して
  ほかを片づける。書き込むのは変えた対象だけ（変えていない対象まで書くと、日時が新しくなって別の端末で同じころに
  決めた額を上書きするため）。端末の時計が大きくずれていると、あとから決めた額が負けることがある（受け入れている）。
- **モデルを足したときの移行は、SwiftData の自動の移行に任せる。** 予算のモデルを足す前の保存先（記録のモデルだけ）を
  開いても、記録はそのまま読め、予算を書き込めることをアプリのテストで確かめている。
- **保存先（`ModelContainer`）は `ModelContainerFactory` でだけ作る**（アプリ・テスト・プレビューのすべて）。
  保存するモデルの一覧（`modelTypes`）もここにあり、モデルを足すときはここに並べる。保存先の場所
  （Application Support/default.store。以前の既定の場所と同じで、変えるとそれまでの記録が読めなくなる）と
  iCloud の扱いを明示する。SwiftData の既定に任せると、iCloud の entitlement を足しただけで利用者の同意なしに
  同期が始まり（`cloudKitDatabase` の既定は `.automatic`）、App Group を足しただけで保存先が共有のコンテナへ移る
  （`groupContainer` の既定も `.automatic`）ため。テストとプレビューのメモリの上の保存先も iCloud を切る。
- **最初から iCloud 同期（SwiftData + CloudKit）の制約に合わせる。** 一意制約を使わない、
  プロパティに既定値を持たせる、関係は任意にする。後から合わせるとデータの移行が要るため。

### 5-3. iCloud の将来計画

- 現在は提供しない。提供するときは任意の機能にし、利用者自身の iCloud の私用データベースに
  保存する。開発者は内容を読めない。
- 家族・パートナーとの共有（プレミアム）は、CloudKit の共有の仕組みを使う想定。
  SwiftData 単体で共有を扱えるかは要確認（§14）。
- 導入するときは `PRIVACY.md` と App Store のプライバシー表示を見直す（§11）。
- いまの保存先は iCloud を明示的に切っている（`ModelContainerFactory.CloudKitDatabase` は `.none` だけで、
  SwiftData の `.automatic` を渡せない）。同期を作るときに、利用者の私用データベースの値を足す。
  設定での切り替えは、画面のツリーを畳み、書き込み中の処理（送信の解析を待ってから記録するものなど。
  `StoreHost.pendingWrites` に数える）が終わるのを待ち、前の保存先を手放してから開き直す形
  （`StoreHost.reopen(cloudKitDatabase:)`）だけを用意した（同じファイルを 2 つの保存先で同時に開かないため）。
  書き込みを待つのは、解析を待つ Task が、画面のツリーを畳んだ後も前の保存先の ModelContext で記録を書き込むため。
  前の保存先がほかから持たれ続けていないか、iCloud へ切り替えたときの動きは、切り替えを作るときに実機で確かめる。
  切り替えの設定のキー（`AppSettings.iCloudSyncEnabled`、既定はオフ）も決めてあるが、まだ使っていない。
- 無料に入れると決めた「iCloud バックアップ」（§6）を何で実現するかは**未決**（§13）。候補は次の 3 つ。
  v1 に入れるかも決めていない。
  - CloudKit の私用データベースへの任意の同期を、バックアップとして出す（上の同期と同じ仕組み）
  - 記録を書き出したファイルを、利用者の iCloud Drive に保存する（CSV 書き出しの延長）。CSV 書き出し（§9 の ⑧）を作ったので、
    共有の画面の「"ファイル"に保存」から iCloud Drive へ手で保存することはいまもできる（書き出した CSV から記録を戻す機能は無い）
  - アプリ側では何もせず、iOS 標準のデバイスのバックアップ（iCloud バックアップ）に任せる。
    この場合、料金表の「iCloud バックアップ」はアプリの機能ではなくなるので、表記を見直す

### 5-4. 保存先のデータ保護

- **SwiftData の保存先は NSFileProtectionComplete にする。** エンタイトルメント
  `com.apple.developer.default-data-protection`（`project.yml` の `entitlements.properties`。
  `SaifuLog/SaifuLog.entitlements` は生成物）で、アプリが作るファイル（`default.store` と
  `-wal`・`-shm` を含む）の既定の保護クラスを Complete にする。既定のクラス（初回のロック解除後は
  常に復号）のままだと、画面のロック中も家計の記録が復号された状態になるため。
- ロック中は保存先を開けない。そのため、保存先（`ModelContainer`）は App の生成の時点ではなく、
  最初の画面が出る時点で開く（`SaifuLog/App/StoreHost.swift` の `start()`）。iOS が起動を前倒しで済ませる prewarm は
  ロック中にも走ることがあり、その間に開こうとしても読めないため。
- **開けなくてもアプリを落とさない。** 以前は開けなければ fatalError で止めていた。いまは `StoreHost` が状態
  （読み込み中・開けた・開けなかった・開き直し中）を持ち、画面（`StoreRootView`）がそれに合わせて出し分ける。
  - ロック中（`UIApplication.isProtectedDataAvailable` が false）は開こうとせずに待ち、ロックが解けた通知
    （`protectedDataDidBecomeAvailableNotification`）か、アプリが前面に来たときに開き直す。開いている途中で
    ロックされて失敗したときも、同じく待つ。
  - ロック中でないのに開けない（空き容量が無いなど）ときは、何が起きたかと「もう一度試す」のボタンを出す。
    黙って空の保存先で続けると、記録が消えたように見えるため。アプリの削除は勧めない（記録が消えるため）。
  - 再試行でもまた開けなかったときは、その回数を画面に出し、VoiceOver にも読み上げ、触覚でも知らせる。
    開けない原因が続いていると、再試行してもすぐに同じ画面に戻り（読み込み中の画面も一瞬も出ない）、
    ボタンが効いていないように見えるため。
- **見直す条件:** ウィジェット、App Intents（Siri・ショートカット）、バックグラウンドの処理などが、
  ロック中に記録を読み書きする必要が出たら、`NSFileProtectionCompleteUnlessOpen` に下げるかを
  決め直す。下げるときは、その理由をここに書く。
- **確かめること:** エンタイトルメントだけで SwiftData の SQLite に効くかは、実機でしか確かめられない
  （シミュレータはデータ保護を効かせない）。ロック中に起動したとき（prewarm など）に落ちずに待ち、ロックを解くと
  ホームが出ることも、同じ理由で実機でしか確かめられない（アプリのテストは、ロックの状態を差し替えて確かめている）。
  実機で `default.store`・`-wal`・`-shm` の保護クラスを確かめるまでは、利用者向けの文書（README・`PRIVACY.md`・
  CHANGELOG）に「ロック中は読めない」とは書かない（ロック中の起動で落ちないことも、実機で確かめるまで書かない）。
  確かめる手段として、社内テスト用のビルド（release.yml の `mode=testflight` で TestFlight の社内テスト専用に送る）と
  DEBUG のビルドに診断画面を入れた。3 つのファイルの保護クラスと、保護されたデータを読めるか
  （`UIApplication.isProtectedDataAvailable`）を出す（`docs/release-flow.md` の「TestFlight で実機に入れる（社内テスト）」）。
- エンタイトルメントは署名ありのアーカイブにしか焼かれず、書き出しの段階の署名し直しも、アーカイブにある
  エンタイトルメントしか引き継がない。そのため release.yml は、開発用の証明書（Apple Development）を使い捨ての
  キーチェーンに取り込み、署名ありでアーカイブする（`docs/release-flow.md` の「署名ありのアーカイブ」）。
  ただし証明書の Secrets の登録も、main で `mode=export` を走らせての確認もまだで、この経路は一度も通していない。
  release.yml はアップロードの前に `make export-ipa` で書き出したアプリをエンタイトルメントのファイルと照合するが、
  確認が済むまでは警告だけにしている（経路のどこかが食い違っていたときに、main へのマージのたびにリリースが
  止まらないように）。**確認が済むまでに送ったビルドに、このエンタイトルメントが載っているとは言えない。**

## 6. 収益化

広告は出さない。**無料版でも記録（AI の文章理解を含む）は無制限。** 端末内 AI は
API 費用がかからないので、いちばん使う機能に上限を付ける理由がない。

| 機能 | 無料 | プレミアム |
|---|---|---|
| ひとこと入力・AI の文章理解 | 無制限 | 無制限 |
| レシート・スクショの読み取り | 月5回 | 無制限 |
| 家計に質問 | 月10回 | 無制限 |
| 週のふりかえり | 簡易版 | ○ |
| 月の AI レポートと予算の提案 | ✕ | ○ |
| 予算 | 全体の予算 | カテゴリ別の予算も |
| 家族・パートナーと記録を共有 | ✕ | ○ |
| iCloud バックアップ・CSV 書き出し | ○ | ○ |

- **プレミアムは買い切り ¥1,800。** サブスクにはしない。ファミリー共有に対応する。試作済み（StoreKit 2。§9 の ⑨）。
- **最初の 14 日間は全機能を無料で開放する。** 支払い情報の登録は求めない。試作済み。体験は利用者が ⑨ の「14日間の無料体験を始める」で
  始める（体験の商品を 0 円で買う形のため、インストールしただけでは始まらない）。
  - 買い切りの App Store アイテムには、サブスクのような無料体験の仕組みが無い。審査ガイドライン
    3.1.1 が認める「非サブスクのアプリが価格 0 の非消耗型アイテム（『14 日間の無料体験』）で期間限定の体験を出す」方式にした。
    端末内の日付だけで数えると、再インストールでやり直せてしまうため。
  - 課金アイテムは App Store Connect に登録済みの 2 つ（製品 ID は変えない。コアの `PremiumProduct`）。
    - `com.iam74k4.SaifuLog.premium`: 非消耗型 ¥1,800（日本基準）、ファミリー共有オン。表示名「サイフログ プレミアム」。
    - `com.iam74k4.SaifuLog.trial14`: 非消耗型 ¥0、ファミリー共有オフ。表示名「14日間の無料体験」。
  - **体験は trial14 の購入日時（`Transaction.purchaseDate`）から 14 日。** 暦の日付ではなく経過時間（14 × 24 時間）で数える
    （`TrialPeriod`）。暦で数えると、時間帯や夏時間の切り替わりで長さが変わり、端末の時間帯を変えるだけで延ばせるため。
    始まりは含み、終わる瞬間からは体験の外。
  - **残りの日数は 1 日単位で切り上げて出す**（残り 1 秒でも「あと 1 日」、始めた直後から 24 時間は「あと 14 日」）。切り捨てると、
    まだ使える最後の 1 日に「あと 0 日」、始めた直後に「あと 13 日」と出て、14 日間という案内と食い違うため。端末の時計が
    購入日時より前にずれていても 14 日を超えては出さない。
  - 体験は 1 つの Apple アカウントにつき 1 回。体験の購入が失効しても（返金などで）、やり直しにはせず、体験は終わったものとする。
  - 体験は無料で、終わっても自動で課金されない（非消耗型なので、続けるかは利用者が買うかどうかで決まる）。⑨ にこのことと、
    期間・終わった後に使えなくなるもの（プレミアムの機能。記録や決めた予算は消えない）を書く（ガイドライン 3.1.1 の体験の説明）。
- **プレミアムの状態は、購入の事実と今の時刻からコア（`PremiumStatus`）が決める。** 購入の事実は StoreKit が端末に持つ
  `Transaction.currentEntitlements` の検証できたもの（オフラインでも読める）に、購入の履歴（`Transaction.all`）のうち失効した体験を
  足したもの（`PurchaseManager.storedPurchases`）。currentEntitlements は返金・失効したものを返さないので、それだけでは体験の返金の
  後の起動や復元で「体験していない無料」に戻り、体験をやり直せてしまうため。アプリは覚えておかない（覚えた値が App Store の記録と
  食い違うと、返金された購入でも使えてしまうため）。
  - 失効していないプレミアムがあればプレミアム。自分で買ったものとファミリー共有の両方があれば、自分で買ったもの（家族が共有を
    やめても使い続けられるほう）。失効したもの（返金・ファミリー共有の取り消し）は数えない。体験中に買ったプレミアムが返金されたら、
    体験の残りに戻る。
  - プレミアムと体験中は、プレミアムの機能をすべて使える。体験が終わったら無料と同じ（体験のボタンは出さない）。
- **無料の回数は暦の月で数える**（`UsageQuota`）。レシートの読み取り月 5 回・家計への質問月 10 回。月はホームの「今月」と同じ、
  利用者が選んだ暦と端末の時間帯の月（`QuotaMonth`。紀元・年・月・閏月で見分ける）。月が替わると 0 から数える。
  - 月の始まりの瞬間ではなく暦の年と月で持つ。瞬間で持つと、同じ月のうちに時間帯を変えただけで別の月とみなし、使った回数を
    0 に戻してしまうため。時間帯を西へ変えて月の境目をまたぎ、前の月に戻ったときも別の月として 0 から数える（前に戻ったときだけ
    数を残すと、時計を先へずらして使った後に直した人が、その月が来るまで使えなくなるため。増えるのは境目をまたいだ間の数回）。
  - プレミアムと体験中は無制限で、使っても数えない（体験が月の途中で終わっても、その月の無料の回数を減らさないため）。
  - 数えるのは読み取りや回答が終わってから（失敗やキャンセルで回数を減らさない）。回数は設定（UserDefaults）に置く（`QuotaStore`。
    家計の中身ではないため）。家計への質問で使っている（数えるのは答えを出せたときだけ。§9 の家計への質問の決め事）。レシートは後で作る。
  - **家計への質問を使い切ったら、答えの代わりにプレミアム（⑨）への案内をタイムラインに出す**（案内のボタンで ⑨ をシートで開く）。
    シートを勝手に開かないのは、入力の途中を遮らないため。記録は無料で無制限のままであることも案内に書く。レシートを作るときも同じ形にするかを決める。
- **バックアップと CSV 書き出しは無料。** データを人質にしないため。CSV 書き出しは試作済み（§9 の ⑧。購入の仕組みを
  作っても、無料のまま出す）。iCloud バックアップの実現方法は未決（§5-3、§13）。
- **App Store Small Business Program に加入する**（手数料 15%）。
- 体験が終わった後の最初の起動で一度だけ、プレミアムの案内（⑨）を出す（§9 の ⑨ の決め事）。

### 6-1. 予算の数え方（v1 の決め事）

- **全体の予算は無料。カテゴリ別の予算はプレミアム。** カテゴリ別の予算の欄は、予算を決める画面（②）をホームと設定から開いたとき、
  プレミアムと体験中だけ出す（開く時点の `PremiumStatus` で決める）。初回の案内の ② では出さない（案内の時点ではまだ体験も購入も
  していないため）。出さないときは決めてあったカテゴリ別の額に触れない（体験が終わっても額は残り、買えばまた出る）。
  **カテゴリ別の予算の進み（使った額との比べ）は、まだどこにも出さない**（§13）。⑨ と予算の画面のカテゴリ別の欄の説明には
  「使った額との比べの表示は近日」と書く（決めた額が何かに効くように読ませないため）。
- **予算は月ごとに持たず、毎月同じ額を使う。** 決め直すと、その月から新しい額で数える。前の月の余りは繰り越さない。
- **予算に数えるのは支出だけ。収入（返金を含む）は予算の支出を減らさない（残りを増やさない）。** 返金を差し引くと、
  給料などの収入まで「使える額」に見えてしまい、どの収入を差し引くかを選ぶ仕組みが v1 には無いため。
- 月は `ReportPeriod.thisMonth`（ホームの今月の合計と同じ、利用者が選んだ暦の月）で区切る。月が変わったら、支出も
  残りの日数も新しい月で数え直す。
- **残りの日数は今日を含めて数える**（9/28 なら 28・29・30 日の 3 日。月末の日は 1 日）。暦で数え、秒数で割らない
  （夏時間の切り替わる日があるため）。うるう年の 2 月は 29 日まで。
- **1 日あたりの額は、残りを残りの日数で割って切り捨てる。** 切り上げると、毎日その額を使ったときに月末に予算を超えるため。
  今日すでに使った分は残りから引いてある。
- 予算を超えたら、残りではなく超えた額（「¥12,000 オーバー」）を出し、1 日あたりの額は出さない。ちょうど使い切ったときは
  超えていない（残り ¥0）。
- 予算の金額は ¥1〜¥99,999,999（入力欄は 8 桁まで）。0 は「設定なし」。
- 月のまとめ（⑦）は、いまの予算をその額に決めた月とそれより後の月にだけ予算の進みを出す（それより前の月の予算は残していない
  ため。§9 の ⑦ の決め事）。

## 7. 外観と配色

- **ライトとダークは iOS のシステム設定に従う。** アプリ内に外観の設定は置かない。
  設定項目を増やさず、iPhone 全体の見た目に合わせるほうが自然なため。
- **配色は「墨 × 山吹」に決めた。** 墨色の文字と温かい白の地に、差し色として山吹を置く。
  値は `SaifuLog/Views/Theme.swift`（`Palette`）にまとめ、画面では色を直接書かない。
  検討していた 3 案（和紙 × 藍・ミント・夜 × アプリコット）と、デザインキャンバスで出した別案は採用しなかった。

| 役割 | ライト | ダーク | 使いどころ |
|---|---|---|---|
| 背景（background） | #F7F6F3 | #121418 | 画面の地、今月の合計の帯 |
| 面（surface） | #FFFFFF | #1C1F24 | 記録の吹き出し、「取り消す」のバナー、入力例 |
| 墨（ink） | #1F1D1A | #F2F1EE | 本文の文字 |
| 補足の文字（inkSecondary） | #5F5B55 | #A8A6A1 | 日付・見出し・入力欄の例・押せない送信ボタンの矢印 |
| 山吹（accentFill） | #F8B500 | #FFC62E | 塗りだけ。送信ボタン、主ボタン（予算の保存など）、選んだ額のボタン、予算の進捗バー |
| 山吹の上の文字（onAccent） | #1F1D1A | #1F1D1A | 塗りの上の文字と記号 |
| 文字の強調（accentText） | #8A5A00 | #FFC62E | ボタンの文字など。Assets の AccentColor（アプリ全体の tint） |
| 注意（danger） | #B3261E | #FF8A80 | 予算オーバー（アイコンと「オーバー」の語を添える）、予算をなくすボタン |
| 収入（income） | #2E7D4F | #7FD1A0 | 収入の金額 |
| 進捗の地（track） | #E4E1DA | #2E3238 | 予算の進捗バーのまだ使っていない分 |

- **山吹は塗りにだけ使う。** 山吹は白地で 1.8:1 しかなく、ライトで文字や細いアイコンに使うと読めない。
  塗りの上の文字と記号は墨にする（白を載せると 2:1 に届かない）。文字の強調は、ライトでは濃い琥珀
  （#8A5A00）、ダークでは山吹にする。
- **アプリ全体の tint は AccentColor だけで決める**（ライトは濃い琥珀、ダークは山吹）。画面の根元に `.tint` を
  掛けるとトグルまで染まるので掛けない。トグルはシステムの色のままにする。
- **色だけで伝えない。** 予算オーバーは、注意の色に加えて警告のアイコンと「オーバー」の語でも示す。選んだ額のボタンは、
  山吹の塗りに加えて VoiceOver に「選択中」と読ませる。予算の進捗バーは数字に添える目安で、数字（残り・超えた額）は
  いつも文字で出す（バーの山吹と地の差は小さく、バーだけでは読み取れないため）。
  収入は、色のほかに「+」の符号と「収入」の語で示している。
- **コントラストはテストで守る。** 文字の組み合わせは 4.5:1 以上、大きい文字とアイコンは 3:1 以上
  （WCAG 2.x の AA）。値を変えて基準を割ると、`SaifuLogTests` の `ThemeContrastTests` が止める。
  AccentColor と `Palette` の値の食い違いも止める。
- 今月の合計の帯は、すりガラスではなく背景と同じ色で塗る（すりガラスは灰色がかり、温かい地から浮くため）。
  帯とタイムラインの境目には、帯の下端に細い線（システムの区切り線）を引く。同じ色のままだと、帯の下で切れた
  吹き出しが帯の一部に見えるため。
- アプリアイコンは「カードがのぞく財布」。ライト（真っ白の地に黒い財布）・ダーク（真っ黒の地に白い財布（ライトの反転））・
  色付き（tinted）の 3 枚で、iPhone の外観設定で切り替わる。元の SVG は `design/icon/`。
  白黒を基調にして配色に依存しないので、**初回のリリースはこのアイコンで出す。**
  配色を決めてもアイコンは作り直さない（変えるなら、初回の手順とは別の作業として扱う）。

## 8. カテゴリ

支出のカテゴリは 8 種。収入は支出とは別の種別として扱う。

| カテゴリ | 色（ライト / ダーク） | 辞書の言葉の例 |
|---|---|---|
| 食費 | 朱 #D9482B / #FF7A5C | ランチ、スーパー、焼肉 |
| 日用品 | 緑 #3E8E41 / #7BCB7E | ドラッグストア、洗剤 |
| 交通 | 藍 #1E6FD9 / #5AA9FF | 電車、バス、タクシー |
| カフェ | 焦茶 #8B5E3C / #C9A27E | コーヒー、カフェ |
| 娯楽 | 紫 #9B40C4 / #C38EF0 | 映画、書籍、本屋 |
| 光熱・通信 | 青緑 #0B7285 / #4FD0E0 | 電気、ガス、水道、スマホ |
| 医療 | 紅梅 #C2185B / #FF7FB0 | 病院、薬 |
| その他 | 鼠 #6E6E73 / #AEAEB2 | どれにも当たらないとき |

辞書の言葉は例。正は SaifuLogCore の `EntryCategory.keywords`。1 文字の語はほかの語の一部に
当たりやすいので、誤爆しにくいもの（「薬」「肉」「魚」「卵」「米」）だけを入れている。「本」は
「日本」「2本」にも当たるので入れない（娯楽の例が「書籍」「本屋」なのはこのため）。短い語に誤って
当たる長い語（「パンツ」の「パン」など）は、その他の辞書で受け止める。

カテゴリの色（`SaifuLog/Views/Theme.swift` の `Palette.category`）の決まり:

- ライトの値は、記録の横の丸の塗りに使う。白い記号を載せて 4:1 以上にしてある（アイコンの基準の 3:1 より
  余裕を持たせた）。丸はダークでもライトの値で塗る（ダークの値は明るく、白い記号が読めなくなるため）。
  食費と日用品は白地で 4.5:1 に届かないので、ライトの値を白地の上の文字には使わない。
- ダークの値は、暗い地の上で文字にも使える明るさ（4.5:1 以上）にしてある。ダークのときの月のまとめの横棒グラフの棒に
  使う（暗い面の上の図形として 3:1 を大きく超える）。内訳の行の丸は、吹き出しの丸と同じくダークでもライトの値で塗る。
- 光熱・通信は、山吹と見分けにくい琥珀をやめて青緑にした。医療はそれまで仮に当てていた青緑を光熱・通信に譲り、紅梅にした。
- システムの色（オレンジや青緑）は明るく、白い記号とのコントラストが足りないため使わない。
- 色だけでカテゴリを見分けさせない。丸にはカテゴリごとの記号を載せ、吹き出しにはカテゴリ名を出す。
  アクセシビリティサイズの文字では、吹き出しに画面の幅を使わせるため丸を省く（カテゴリ名は常に出る）。

- ⑤ を別の画面にせずタイムラインのカードにするのは、レシートの記録もひとこと入力と同じ
  流れに並べるため。
- **初回の案内（① → ②）は一度だけ出す。** 終えたかどうかは設定（UserDefaults の `hasCompletedOnboarding`）に書く。
  ② で予算を保存しても、「あとで」で飛ばしても終えたことになる（予算はホームの帯からいつでも決められる）。② の保存に
  失敗したときは終えず、② に残る。途中でアプリを終了したら、次の起動でまた ① から出す。
- **記録が 1 件でもある端末には、案内を出さない**（案内を作る前の版から使っている人に、使い方の例を見せ直さないため）。
  そのときは出さずに終えたことにしておく。そうしないと、あとで記録をすべて削除した後の起動で案内が出てしまう。
  記録があるかを読めなかったときは、終えたかどうかだけで決める（案内が出るだけで、記録には触れない）。
  予算だけが決まっていて記録が無い端末には出す（② には決めた予算が入って開く）。
- 案内はホームに重ねる全画面のカバーではなく、保存先を開いた後の最初の画面の切り替え（`AppRootView`）にする。カバーは
  出す動きを消せず、初回の起動でホームが一瞬見えてから案内が下から上がってくるため。案内の間はホームを作らない。
- ① の入力の例は「ランチ 850」「昨日 焼肉12000 4人で割り勘」「今月カフェいくら?」（3 つ目は質問の例。家計への質問を作ったので、
  「スーパー2480とドラッグ1200」から差し替えた。記録も質問も同じ入力欄に打てることを最初に見せるため）。どれも AI が無くても
  キーワード辞書で同じように記録・回答できるもの（アプリのテストで確かめる）にし、記録のされ方には AI と辞書で変わりうるものを
  書かない。金額・日付・割り勘の人数・件数はコアが入力の文と突き合わせるので同じになるが、カテゴリは品目が文に書かれて
  いればモデルの答えを採る（§15 の 3）ので、「ランチ」の食費も含めて書かない。質問の例は「今月のカフェの支出を答える（記録はしない）」
  と書く（期間とカテゴリは文からコードが読み、「いくら」だけの文はモデルが何を選んでもカテゴリの支出で答える（§3-4）ので、AI の有無で
  変わらない）。AI が使えない機種の案内も「記録や質問ができます」にした。
  例の文は日本語のまま見せる（解析が日本語の入力を前提にしているため）。ホームの記録が無いときの案内も、記録の 3 つの例に加えて、
  「同じ入力欄で、家計について聞くこともできます」と質問の例（「今月カフェいくら?」）を出す。
- ① の AI の案内は、使えるとき・Apple Intelligence に対応していない機種・オフ・準備中（モデルのダウンロードなど）・
  そのほかで文を分け、どの場合も記録はできることを伝える（オフなら設定でオンにできること、準備中なら済めば AI が読むことも
  添える）。可否は覚えておかずに描くたびに読むので、案内を見ている間に使えるようになれば文が替わる（Foundation Models の
  `SystemLanguageModel` の変化を画面が拾う想定。実機で確かめる）。
- ① の記録の置き場所は「この iPhone の中に保存し、文の読み取りもこの iPhone の中で行う。開発者のサーバーはなく、記録や
  入力した文を開発者や第三者に送らない」と伝える。iCloud 同期（§5-3）を利用者が選べるようにしても食い違わない言い方にしてある。
- ② は初回の案内・設定・ホームのシートで同じ中身（`BudgetSetupView` と `BudgetSetupModel`）を使い回す。開けるのは
  初回の案内（① の「はじめる」から横に進む）と、ホームの帯のボタンからのシートと、⑧ の「月の予算」の行からのシート（ホームと同じ
  `BudgetSetupSheet`）。予算を決めた後は帯のボタンが「予算を変更」になる（⑧ を作った後も帯に残す。⑧ の決め事）。数字のキーボードには確定のキーが無いので、
  保存のボタンは画面の下に置き続ける（キーボードが出るとその上に移る）。
- **② の「予算をなくす」は、確認のダイアログ（「予算をなくしますか？」、破壊的なボタン「予算をなくす」とキャンセル）を
  挟んでからなくす**（`BudgetSetupModel.requestRemoveTotalBudget`）。押しただけで消すと、シートが上がる途中の誤タップで
  予算が消えていた（シミュレータで確かめた）。VoiceOver のダブルタップも同じ操作なので、同じ確認が出る。ダイアログは
  ボタンに付ける。iOS 26 ではボタンを指す吹き出しの形で出て、キャンセルのボタンは出ず、外を押すとキャンセルになる
  （シミュレータの iOS 26.4 で、外を押すと予算が残り、「予算をなくす」を押すとなくなってシートが閉じることを確かめた）。
- ホームの帯は、予算を超えたら見出しを「今月の予算」にし、「¥… オーバー」を注意の色・警告のアイコン・語で出す。
  VoiceOver では帯の数字を 1 つの要素にまとめ、見出し・残り（超えた額）・1 日あたり・残りの日数・予算・使った額・収入の
  順に読ませ、ボタンはその後に置く。予算と使った額は画面には出さない（予算は超えたときだけ出す）が、読ませない進捗の
  バーの代わりに読ませる。帯の「1日あたり ¥… ・のこり N 日」の区切りの点も訳す（英語では中点「·」）。
- ⑦ と ⑧ を横に進む画面にするのは、ホームから行って戻るだけの画面だから。⑥ と ⑨ は
  用が済めば閉じる一時的な画面なので、下から出すシートにする。
- 記録の削除は、③ のタイムラインの吹き出しの長押しから行う（§2）。⑥ を作っても長押しの削除は残し、⑥ の「この記録を削除」
  からも消せるようにした。
- **家計への質問の決め事**（`HomeModel` の送信、回答カードは `Views/Question/`、答え方は `AI/QuestionAnswering`、数字と見分けはコア）:
  - **記録か質問かは、コア（`InputIntentClassifier`）がコードで決め、誤って記録にならないことを優先する**（質問の文を支出として保存すると、
    合計が黙って狂うため）。上から順に、(1)「?」（全角も）・「いくら」・「どれくらい」・「何円」・「何件」・「何回」・「教えて」・「ですか」などの
    はっきり質問を表す語があれば、金額があっても質問（「いくら丼」は品目として見ない）。(2) 記録として読める金額（記録の読み取りと同じ
    `EntryInput` で 1 件以上。直近 N 日の日数と「1日あたり」の 1 は数えない）があれば記録。ただし「残り」「使える」「予算」「収支」「件数」「内訳」、
    後ろに金額の続かない「合計」も含むなら、決められない。「スーパー 合計2480」のように金額を添えた「合計」は記録の書き方（§4-4 の添えた額）
    なので記録のまま。「使った」「一番」は「コンビニで使った 500」「一番搾り 300」のように記録にも書くので、決められない語に入れない。
    (3) 金額が無ければ、質問の語（「合計」「使った」「支出」「収入」「予算」「一番」「何」など）があるか、期間の語にカテゴリの表示名が続くか
    （「先月の食費」）、期間の語だけ（「先月」）なら質問。それ以外（「ランチ」「昨日 ランチ」）は記録として扱い、これまでどおり「金額が
    見つかりませんでした」を出す（金額を書き忘れた記録を、質問として答えないため）。
  - **決められないとき（金額と質問の語が両方ある）は、記録も回答もせず、確認のダイアログも出さない。** タイムラインに「記録か質問か
    分かりませんでした」と、記録なら金額と品目だけ・質問なら「?」を付けて送ることを案内し、送った文を入力欄に戻す（書き直して送り直せる）。
    確認のダイアログにしないのは、一行入力の軽さを崩さないため（決められない文はまれで、書き直すほうが速い）。無料の回数は数えない。
    送った文は質問と同じ右寄せの吹き出しに出すが、「?」の丸は付けず（丸の幅は空けてほかの吹き出しと端をそろえる）、VoiceOver でも
    「質問: …」ではなく「送った文: …」と読む（下の案内が「分かりませんでした」と言うのに、吹き出しが質問と名乗ると食い違うため）。
  - **質問はホームのタイムラインに、記録の吹き出しと同じ流れ（送った順）で出す。** 送った質問は右寄せの吹き出し（記録のカテゴリの丸の
    代わりに「?」の丸）、返事は左寄せのカードにする（自分が送ったものとアプリからの返事を見分けるため）。**質問と答えは保存しない**
    （記録ではなく、アプリを開き直すと消える）。保存すると記録と同じ保存先・iCloud 同期・CSV 書き出しの扱いを決めることになるうえ、
    答えは送ったときの数字の写しで、記録を直すと古くなるため。答えを待つ間は「計算しています…」を出し、送信ボタンを押せなくする
    （記録の読み取りと同じ）。質問を送ったときも、前の記録の「取り消す」は引っ込める（送るたびに引っ込める、と揃える）。
  - 回答カード: 期間の名前と日付（「今月・9月1日～30日」）、見出し（「カフェの支出」「予算の残り」など）、大きな数字（コードが計算した値。
    桁の途中で折り返さず、収まらなければ縮める）、数字に添える内訳（いちばん使ったカテゴリの名前と割合、カテゴリ別の行、予算と使った額、
    残りの日数）、元になった記録の件数、AI の一言（ある場合。照合を通ったものか定型文「数字はアプリが記録から計算しました。」）、無料の
    残りの回数（3 回以下のとき）。予算を超えた額は注意の色にアイコンと「オーバー」の語を添える（色だけに頼らない）。1 行に収まらなければ
    アイコンを上に置き、額の行に幅を使わせる（折り返すと「¥」と数字の間で切れたため。カードを画像にして確かめた）。
  - **今月・先月の答えは、カードを押すとその月の月のまとめ（⑦）を開く**（「›」を添え、VoiceOver では「月のまとめを開きます」）。
    予算の答えは今月（先月の予算の残りは先月）で数えるので、同じく開ける。今日・今週・直近 N 日・今年は月まるごとではないので開かない。
  - 予算を決めていなくて予算の残りや 1 日あたりの額に答えられないときは、そう書いて「予算を決める」（② のシート）を出す（答えたので数える）。
  - 読めなかった質問は、質問の例（「今月カフェいくら?」「先月の食費は?」「今月あと何日でいくら使える?」「今週いちばん使ったのは?」。
    日本語のまま）と答えられる期間を出し、送った文を入力欄に戻す（数えない）。
  - **答えられる期間は今日・昨日・今週・先週・今月・先月・今年と、直近 N 日（1〜366 日。「直近7日」「過去30日間」「ここ1週間」）。**
    期間が書かれていなければ今月。今週・先週は ⑧ の週の始まりに従う（画面の暦の `firstWeekday`）。「去年」「来月」「明日」「一昨日」「週末」
    「金曜」「9/26」「3日前」のような期間や日付、「今月と先月」のような 2 つの期間、金額を含む質問は、黙って今月として答えると聞かれて
    いない期間の数字になるので、読めない質問にする（AI にも渡さない）。「8月の食費」「2025年の支出」「令和7年」「この一年」のように
    数字で名前を付けた月や年と、「半年」「今年度」も、いまは読めない質問（日の無い「8月」は日付の読み取りが日付とみなさないので、
    質問の読み取りで数字の後ろの「月」「年」を見て止める。月の名前は、あとで `ReportPeriod.month` で足すかを決める）。
    「最近いくら使った?」のように日数の無い「最近」は、期間が書かれていない質問として今月で答える。
  - **1 日あたりの言い回しは、予算の語と一緒のときだけ 1 日あたりに使える額にする。** 「1日あたり」「1日で」「毎日」「日割り」は、
    「使える」「残り」「予算」「まで」「あと」などと一緒なら 1 日あたりに使える額（「何日で」「あと何日」はいつも）。予算の語が無いときは、
    「今日1日でいくら使った?」の「今日1日で」はその日まるごととして読み飛ばし（今日の支出の合計）、「先月は1日にいくら使ってた?」
    「毎日いくら使ってる?」「1日あたりいくら使った?」のような 1 日あたりに使った額（平均）と、「今月1日に」の日付、予算の語の無い
    「毎日」は読めない質問にする（使った額を聞かれたのに、今月の予算の 1 日あたりの額を答えて無料の回数を使わせないため）。予算の語も
    使った額を聞く語も無い「1日あたりいくら?」「日割りでいくら?」は 1 日あたりに使える額として答える。
  - **予算は月の全体の予算だけで答える**（カテゴリ別の予算の進みは、まだどこにも出さない決め事のため。§6-1）。予算の残りは先月を聞かれたら
    先月（いまの予算を先月の終わりより前に決めていたときだけ。⑦ と同じ）、それ以外は今月で数え、数えた期間をカードに出す（聞かれた期間と
    違うことが分かるように）。1 日あたりに使える額はいつも今月（残りの日数は今日を含む。§6-1）。
  - 元になった件数は、数えた記録の件数（支出の合計・内訳・いちばん使ったカテゴリ・予算は支出の件数、収入は収入の件数、収支とカテゴリを
    聞かれていない件数は支出と収入の件数、カテゴリの支出はそのカテゴリの支出の件数）。件数も合計と同じ区切り（`LedgerSummary`）で数える。
  - **無料の回数（月 10 回）は、答えを出せたときだけ数える**（読めなかった・決められなかった・失敗・使い切った後は数えない）。答えを待つ間に
    体験を始めたり買ったりしていれば数えないよう、答えた後の状態で数える。起動の直後で購入の事実をまだ読み終えていなければ、読み終える
    のを待ってから使い切ったかを決める（読み終える前は、プレミアムや体験中でも無料に見えるため。使い切った後に買った人に使い切りの案内を
    出したり、プレミアムの人の質問を数えたりしないように。体験の終わりの案内と同じ）。使い切ったら答え手を呼ばず、答えの代わりにプレミアムの案内を
    出して送った文を入力欄に戻す（買った後に送り直せるように）。プレミアムと体験中は無制限で、残りの回数も出さない（§6）。
  - 答えに使う記録は、送った瞬間に保存先から値だけの写し（`QuestionLedger`）にする。AI のツールはメインスレッドの外で呼ばれて ModelContext を
    使えず、どの期間を聞かれるかも先に分からないので、答えうる期間をすべて覆う範囲（今年・先月・先週・直近 366 日）を読む。読むだけなので
    `StoreHost.pendingWrites` には数えない。
  - VoiceOver: 質問の吹き出しは「質問: …」（決められなかった文は「送った文: …」）、回答カードは期間・見出し・数字・件数・一言を 1 つの
    要素として読む。答えが届いたら、期間・見出し・数字・件数・AI の一言と、無料の残りの回数（カードに出す 3 回以下のとき）を読み上げる
    （カードが出るだけでは伝わらないため。残りの回数もカードの小さな行だけでは気づけない）。読めない・決められない・使い切ったときも
    見出しを読み上げる。
    入力欄のラベルは「記録や質問」にした。
  - 山吹の塗りは使わない（塗りの主ボタンが無いため）。「予算を決める」「プレミアムを見る」は tint（AccentColor）の文字。アクセシビリティ
    サイズの文字では、質問の吹き出しの「?」の丸と内訳の行の丸を省き、内訳の金額と割合は収まらなければ名前の下に積む。
- **⑥ 直すの決め事**（`EditEntrySheet` と `EditEntryModel`）:
  - 金額は ¥1〜¥999,999,999,999（ひとこと入力が金額として読む上限と同じ。`EntryAmountInput`）。上限を下げると、ひとことで
    記録できた額の記録を開いたとき、金額を変えずにカテゴリだけを直すこともできなくなるため。空欄・0 円・上限を超えた額は
    保存できず、入力欄の下に理由を出す（注意の色に、アイコンと文を添える）。入力欄は上限の桁数より 1 桁多くまで残す
    （上限の桁数で切ると、打った 13 桁目が黙って消え、打ったつもりと違う額を保存しかねないため）。
  - 日付は日だけを選び、時刻は元の記録のものを残す（`EntryDateEdit`。日は暦で数えて足し、夏時間の日にも時刻がずれない）。
    今日より先の日付は注意を出すだけで保存できる（払う予定の家賃のように、先の日付で記録することがあるため。§4-4）。
  - 収入に直したら、カテゴリは「その他」で保存する（ひとこと入力で収入を記録したときと同じ）。収入のときはカテゴリの欄を出さない。
  - 直していなければ保存を押せない。品目は前後の空白を除いて比べて保存する。
  - 直した内容があるときは、下へのスワイプでもキャンセルでも、破棄してよいかを確かめてから閉じる。スワイプは
    `interactiveDismissDisabled` で止め、止めたことを UIKit の知らせ（`presentationControllerDidAttemptToDismiss`）で受け取って
    確認を出す（SwiftUI には受け取る方法が無いため、SwiftUI の delegate を包んで、ほかの知らせはそのまま渡す）。受け取れなかった
    ときは、スワイプで閉じないだけで、キャンセルから確認を出せる。
  - 保存に失敗したら、シートは閉じずにアラートを出す。記録は直す前の値に戻し、入力欄は残す（閉じると打ち直しになるため）。
  - 直前に記録したものを直したら、「取り消す」を引っ込める。取り消すと直す前の送った文が入力欄に戻り、直した内容と食い違うため。
    直さずに閉じたときは「取り消す」を残す。シートを出している間はバナーを時間で引っ込めるタイマーを止め、閉じたら数え直す
    （シートの下でも数え続けると、直すのに時間をかけてやめたときには「取り消す」が消えているため）。保存の失敗のアラート
    （取り消せなかったときなど）を出している間も同じく止め、閉じたら数え直す。
  - 直した内容はホームの帯（今月の合計と予算の残り）にすぐ反映する（帯は保存先の今月の記録を読み直す）。日付を直しても、
    タイムラインの並びは送った順のまま（記録した日時は直さない）。
  - 山吹は保存のボタンの塗りにだけ使う。選んだ種類とカテゴリは、墨の枠とチェックの印で示し、VoiceOver には「選択中」と読ませる。
    カテゴリは色と記号の丸を添えて並べる（アクセシビリティサイズの文字では 1 列、種類も縦に積む）。
  - VoiceOver では、吹き出しのダブルタップで ⑥ を開き、操作の一覧に「直す」「削除」を出す。記録の直後は、入力欄の操作の一覧にも
    「直す: ランチ ¥850」を出す（送信の後にフォーカスが入力欄に戻るので、読み上げで読み違いに気づいたらその場で直せるように）。
    保存したら「直しました: ランチ 食費 ¥900」（今日でなければ日付も）を読み上げる。
- **⑦ 月のまとめの決め事**（`MonthlyReportView`・`MonthlyReportModel`、数字はコアの `MonthlyReport`・`CategoryBreakdown`）:
  - 入口はホームの帯（今月の数字）。見出し（「今月あと ›」「今月の支出 ›」「今月の予算 ›」）と数字のどちらを押しても開く。ホームは
    ナビゲーションバーを出さずにタイムラインを広く使っているのでツールバーには置かず、帯に別のボタンも足さない（帯の右は
    「予算を決める」「予算を変更」のボタン）。今月の合計を見て「何に使ったか」を知りたくなる場所なので、そこを入口にした。
    VoiceOver では帯の数字の要素がボタンになり、「月のまとめを開きます」と説明を読む（見出しは読ませない。2 回読まれるため）。
  - 開くと今月を出す。月は `ReportPeriod`（ホームの今月と同じ、利用者が選んだ暦の月）で区切る。月送りは、今月より先には
    進めない（先の日付の記録があっても）。記録のある最初の月（使った日時のいちばん古い記録の月）より前にも戻れない。途中の
    記録の無い月は通れる。月を替えたら、月の見出しを VoiceOver に読み上げる（ボタンにフォーカスが残り、どの月になったかが
    読まれないため）。前面に置いたまま月をまたいでも、見ている月は替えない（次の月へ進めるようになる）。
  - 支出・収入・収支に加え、1 日あたりの平均を出す。平均は支出を日数で割って四捨五入し、割る日数は、終わった月はその月の
    日数、今月は 1 日から今日まで（今日を含む）。今月を月の日数で割ると、月の半ばでは平均が実際の半分ほどに見えるため。
    予算の 1 日あたりの額（切り捨て）と違い、使える上限ではなく過ぎた日のようすなので、いちばん近い整数にした。
    **平均（と今日までの目安との比べ）に数える支出は、今日の終わりまでの日付の記録だけ**（`MonthlyReport.expenseThroughToday`）。
    今月には先の日付の記録（払う予定の家賃など。§4-4）を付けられるので、月の支出まるごとを今日までの日数で割ると、まだ来て
    いない日の支出で平均が上がる（9/28 に 9/30 の家賃 ¥80,000 を付けると 1 日あたり約 ¥2,857 上がる）ため。今日の、いまより
    後の時刻の記録は数える（割る日数に今日を含めているため）。月の支出と予算の使った額は、ホームの帯と同じく先の日付の記録も
    含めた月まるごとのまま出す。
  - 前の月との差（この月の支出 − 前の月の支出）は、前の月に支出の記録が 1 件も無ければ出さない（使い始めた月の翌月に
    「前月より（まるごと）多い」と出ても比べたことにならないため。収入だけの月も、支出をつけていなかった月とみなす）。
    多い・少ないは矢印だけでなく語でも示す（色は変えない。多く使ったこと自体は注意ではないため）。
  - **予算の進みは、いまの予算をその額に決めた月（月の途中で決めてもその月）と、それより後の月にだけ出す。** 予算は月ごとに
    持たない（§6-1）ので、それより前の月の予算がいくらだったかは分からず、いまの額で比べると違う予算で「超えた」「余った」と
    出してしまうため。決めた日時は、いま有効な予算の行の書き込んだ日時（`BudgetPlan.decidedAt`）。予算を書くとき
    （`BudgetStore.setAmounts`）は、有効な行の額が同じなら行を書き換えない（書き込んだ日時を動かさない）ので、その日時より後は
    ずっとその額だったと言える。予算を決める画面も変えた対象だけを渡すが、保存先を読めずに空で開いたときは同じ額でも変えた
    ものとして渡すので、書くところで守る。月ごとの予算の履歴は持たない
    （持つならモデルを足すことになる）。今月だけは、日割りの目安（予算 × 1 日から今日までの日数 ÷ 月の日数、切り捨て）と
    その差（「今日までの目安より ¥… 少ない」）を出し、バーに目安の印（墨の縦線）を立てる。差は今日の終わりまでの日付の支出で
    比べ（平均と同じ理由）、先の日付の記録があって使った額と違うときは、比べた額を「今日までに使った額」の行で添える（使った額と
    目安の差に合わない数字を、わけを示さずに出さないため）。バーは使った額（月まるごと）のまま。今日を含めるのは、予算の残りの日数が
    今日を含めているのと合わせるため。印はバーの上下にはみ出させる（ダークでは墨が明るくなり、山吹の塗りの上では見分けにくいため）。
  - カテゴリ別の内訳は、支出だけを金額の多い順（同じ額はカテゴリの定義順）に並べ、0 円のカテゴリは出さない。割合は最大剰余法で
    整数の % に丸め、合計をちょうど 100 にする（1 つずつ四捨五入すると 99% や 102% になるため）。端数の大きい行から 1 ずつ足し、
    端数が同じなら上の行から足す。ごく小さい額は 0% になるので、画面では「<1%」と出し、VoiceOver には「1パーセント未満」と読ませる。
  - 横棒グラフ（Swift Charts）の棒はカテゴリの色（`Theme`）で塗り、VoiceOver では棒ごとに「食費」「¥12,300 42%」と読ませる
    （オーディオグラフでも同じ値をたどれる）。グラフの下に同じ内容の行（色と記号の丸・名前・金額・割合）を並べ、行を押すと
    その月のそのカテゴリの支出の記録の一覧へ進む。一覧は読むためのもので（使った日時の新しい順）、記録を押すと ⑥ を開き、
    直したり消したりすると、まとめの数字と一覧をすぐ読み直す（カテゴリや月を変えた記録は一覧から外れる）。まとめから直したり
    消したりしたときも、ホームから直したときと同じく「取り消す」を片づける。
  - アクセシビリティサイズの文字では、グラフを出さずに行（表）だけにする（棒の横に名前を収める幅が無く、行と同じ内容のため）。
    行・金額の行は 1 行に収まらなければ縦に積み、矢印は省いて語だけにする。
  - 山吹は予算のバーの塗りにだけ使う。月送りの矢印も墨にし（押せないときは薄くする）、超えた額は注意の色・アイコン・語で出す。
  - 記録の無い月は「この月の記録はありません」（今月なら、入力欄から送るとここに出ることを添える）だけを出す。
  - 保存先に書き込まれたら（`ModelContext.didSave`）読み直す。まとめを開く直前に送った文の読み取り（AI だと 1 秒以上かかる）が、
    開いた後に記録されることがあるため。iCloud 同期を足すときは、ほかの端末からの変更でも読み直すようにする。

    結果の数（通った・失敗・飛ばした）をログに出し、1 つでも飛ばされたか 1 つも通らなければ失敗にする（`scripts/test-storekit.sh`）。
    build.yml は、ランナーのイメージにその版のランタイムが無ければ入れてから動かす（`scripts/prepare-storekit-simulator.sh`）。ほかの版で
    動くと確かめたら `STOREKIT_TEST_OS` を変える。SKTestSession ではファミリー共有の購入を
    作れないので、ファミリー共有は購入の事実を差し替えて確かめる。SKTestSession の `setSimulatedError(nil, forAPI:)` は、iOS 26.2 の
    シミュレータで次の購入を失敗させた（「Server canceled the purchase」）ので、起こした失敗はセッションを作り直すとき
    （`resetToDefaultState()`）に消す。
- **⑧ の CSV 書き出しの決め事**（中身はコアの `LedgerCSVWriter`、ファイルは `LedgerExporter`）:
  - 書き出すのは、利用者が設定で「CSV ファイルを書き出す」を押したときだけ。期間（今月・先月・今年・すべて。`LedgerExportPeriod`。
    区切りは `ReportPeriod` で、ホームやまとめと同じ暦の月と年）を選び、書き終えたら iOS の共有の画面を出す。渡す先は利用者が
    選び、アプリからは送らない（`PRIVACY.md`）。期間は開くたびに今月から始める。
  - 形式は UTF-8 の BOM つき（BOM が無いと、日本語版の Excel が Shift_JIS として読み、日本語が文字化けするため）で RFC 4180。
    行の区切りは CRLF（最後の行の後にも付ける）。カンマ・改行（CR か LF）・ダブルクォートを含む値はダブルクォートで囲み、中の `"`
    は `""` にする。列は 日付（yyyy-MM-dd）・時刻（HH:mm、24 時間）・種類（支出／収入）・カテゴリ・品目・金額・送った文。日付と
    時刻は端末の時間帯の西暦で書く（和暦などの暦を使っていても、表計算ソフトが日付として読めるように）。並びは使った日時の
    古い順（同じなら記録した順）。
  - 見出しと値（種類・カテゴリ）は、アプリの表示の言語で書く（英語で表示しているときだけ英語、それ以外は日本語。画面と同じ決め方）。
    言葉は画面と同じにし、英語は String Catalog の訳と一致することをアプリのテストで確かめる。品目と送った文は訳さない。
  - 収入の行のカテゴリは空にする。収入はカテゴリで分けておらず（ひとこと入力は「その他」で保存する）、「その他」と書くと
    支出のその他と見分けが付かないため。収入のカテゴリを分けると決めたら（§13）ここも見直す。
  - 金額は整数で、「¥」も桁区切りも符号も付けない（表計算ソフトで数として合計できるように。支出か収入かは種類の列で分かる）。
  - **数式インジェクション対策**（OWASP の CSV Injection の推奨）: `=` `+` `-` `@` タブ CR で始まる値の先頭に `'` を付ける。
    品目と送った文は利用者が打った文なので、`=HYPERLINK(...)` のような文が表計算ソフトで数式として動かないようにする。
    **金額の列には付けない。** 保存する金額は正の整数だけで、書くのは数字だけ（先頭が `-` にもならない）なので数式にならず、
    `'` を付けると数として合計できなくなるため。日付・時刻・種類・カテゴリはアプリが決めた文字で、先頭がこれらの記号になることは無い
    （同じ処理は通している）。
  - 記録の無い期間を選んだら、ファイルを作らずに「書き出す記録がありません」と知らせる（見出しだけのファイルを渡しても使えない
    ため。コアは見出しの行だけを返す）。
  - **記録が 1 万件でも画面を止めない。** 保存先から読み、CSV にし、ファイルに書くまでをメインスレッドの外で行い（ModelContext は
    スレッドをまたげないので、同じコンテナから書き出しのための ModelContext を作る）、その間はボタンを「書き出しています…」に
    して進行中の印を出す。読むだけで書き込まないので、`StoreHost.pendingWrites` には数えない。メインスレッドの外で進むのは
    `LedgerExporter.export` の `@concurrent` だけが支えているので、アプリのテスト（`SettingsModelTests`）で、1 万件の書き出しの
    途中（保存先から読み始める直前）にメインスレッドにいないことと、メインアクターに積んだ処理が書き出しの終わりを待たずに動くことを
    確かめる（`export` を `@MainActor` に替えると落ちることを確かめた。`@concurrent` を外して呼んだ側のアクターで動く設定
    （NonisolatedNonsendingByDefault）を入れたときも、メインアクターの上で進むので落ちる）。実機での体感は「これから」で確かめる。
  - ファイルは一時ディレクトリの書き出し専用の場所に、書き出しのたびに使い捨てのディレクトリを作り、`saifulog-YYYYMMDD.csv`
    （書き出した日。端末の時間帯）で置く。保護クラスは Complete（保存先と同じ扱い）。共有の画面を閉じたら（渡し終えたか、
    やめたか）ディレクトリごと消す（家計の記録の写しをアプリの中に残さないため）。設定の画面を離れたら途中の書き出しをやめ、
    共有の途中でアプリが終了したときなどに残ったものは、次に設定を開いたときに消す。共有の画面を出している間は次の書き出しを
    受け付けない。
  - 共有は SwiftUI の ShareLink ではなく UIActivityViewController で出す。ShareLink には共有を終えたことを知る方法が無く、
    終わったらファイルを消すことができないため。共有の画面には「"ファイル"に保存」も並ぶので、fileExporter は置かない。
    吹き出しの基準（sourceView）は渡さない（iOS 26 の iPhone では、渡すと画面全体を指す吹き出しの形になり、下から出る共有の
    シートにならなかった。シミュレータの iOS 26.4 で確かめた）。
  - 共有を終えたことは `completionWithItemsHandler` で知るが、この知らせは共有の画面を閉じたときだけでなく、選んだ先（メール・
    メッセージ・「"ファイル"に保存」など）の画面を閉じるたびにも来る。先の画面でやめると、共有の画面は出たまま「やめた
    （completed が false、先の種類あり）」で来るので、そこでファイルを消すと、続けて別の先を選んだときに渡すファイルが無くなる。
    そのため、先の種類が無い（共有の画面を閉じた）か、渡し終えた（この後に共有の画面は閉じる）か、UIKit の上で共有の画面が
    もう出ていないときだけ終える（判定は `ShareSheetPresenter.Coordinator.sheetHasClosed`。アプリのテストで確かめる）。
  - 共有の画面を出せなかったとき（ほかの画面が出たり閉じたりしている途中など）は出し終えた知らせが来ないので、2 秒待っても来ず、
    UIKit の上でも出ていない（出している途中でもない）ときだけ、出せなかったことにしてファイルを消し、ほかの失敗と同じく
    「書き出せませんでした」と知らせる（書き出しのボタンが押せないままにならないように。押して進行中の印が出た後、何も起きずに
    終わると何があったのか分からないため）。UIKit の状態も見るのは、実機では最初の共有の画面を出すのに時間がかかることがあり、
    出している途中や出し終えた直後に消すと、出てきた画面が無いファイルを渡すことになるため。それでも遅れて出てきたら、渡す
    ファイルはもう無いので閉じる。この出し入れの順（終えるのは一度だけ・出し終えた後の待ちは何もしない・前のファイルの待ちは
    次の書き出しを終えない）は、UIKit から切り離した `Coordinator` でアプリのテスト（`ShareSheetCoordinatorTests`）にしている。
  - シミュレータの iOS 26.4 で、「"ファイル"に保存」で保存すると一時ファイルが消え、保存したファイルは中身がそのままであること、
    共有の画面を閉じるだけでも一時ファイルが消えることを確かめた。先の画面でやめてから同じ共有の画面で別の先に渡すことと、
    最初の共有の画面が遅く出るときの動きは、まだ実機で確かめていない（「これから」）。
- **画面は縦向きだけにする**（`project.yml` の `INFOPLIST_KEY_UISupportedInterfaceOrientations_iPhone`）。
  横向きでキーボードを出すと、タイムラインがほとんど見えなくなるため。
- iPad 向けのレイアウトは作らない（`TARGETED_DEVICE_FAMILY = 1`）。ただし iPhone 専用のアプリも
  iPad の App Store で配信され（外せない）、iPad では iPhone 版が拡大して動く。審査も iPad で
  行われることがあるので、iPad でも動くことは確かめる（`docs/release-flow.md`）。
- 文字サイズは、アクセシビリティサイズまで崩れないようにする。金額は桁の途中で折り返さない
  （1 行に収まらなければ縮める）。画面の上に常に出る今月の合計は、文字の大きさに上限を設けて、
  タイムラインの場所を残す。帯の「1日あたり ¥… ・のこり N 日」や見出しとボタンの行は、1 行に収まらなければ
  縦に積む。予算の入力欄は文字を縮められない（はみ出す）ので、文字の大きさに上限を設ける。すぐ選べる額のボタンは、
  1 行に収まらなければ縦に並べる。
  ① は縦にスクロールし、「はじめる」は画面の下に置き続ける。アクセシビリティサイズでは案内の横の記号を省き、飾りの印の
  大きさに上限を設ける。入力の例は、打つ文と記録のされ方を横に並べず、いつも縦に積む。
- VoiceOver では、① は見出し（アプリの説明・入力の例・AI の案内・記録の置き場所）の順に読める。入力の例は「入力例」と
  打つ文・記録のされ方を 1 つの要素として読み、「はじめる」「あとで」には行き先を説明として読ませる。案内を終えて
  ホームに切り替わったら、切り替えの動きが済んでから画面が替わったことを VoiceOver に知らせる（根元の画面の切り替えは、
  横に進む・シートと違って VoiceOver に伝わらず、フォーカスしていたボタンが消えて行き先が決まらないため）。ホームの
  最初の要素にフォーカスが移り、② の保存の「予算を ¥… にしました」はその前に読ませる（実機で確かめる）。

## 11. プライバシー表示の方針

- App Store のプライバシー表示は「**データの収集なし**」を目指す。端末内の保存と端末内の
  AI の処理は、開発者が受け取らないので「収集」にあたらない。
- 解析や広告の SDK を 1 つでも入れると、表示と `PRIVACY.md` の両方が崩れる。入れない。
- iCloud（CloudKit の私用データベース）も開発者は読めないが、導入するときに表示を見直す。
- **課金（プレミアム・14 日間の体験）を足しても「購入」は収集しない。** 購入と支払いは Apple の StoreKit が扱い、アプリは端末の上で
  購入の記録（`Transaction.currentEntitlements` と、返金された体験を見分けるための `Transaction.all`）を読んでプレミアムかどうかを決めるだけで、購入の情報を開発者のサーバーへも第三者へも
  送らない（サーバーを持たない）。App Store のプライバシー表示の「購入（購入履歴）」は、開発者やその協力者が受け取るデータを申告する
  もので、Apple が StoreKit の中で扱う購入は含まないので、「データの収集なし」のまま出す。App Store Server Notifications や
  App Store Server API で購入の記録を開発者の側に受け取るようにしたら、表示と `PRIVACY.md` を見直す。
- `PRIVACY.md` には「端末の外へ送らない」と書き、「通信機能を持たない」とは書かない。
  将来 iCloud を入れる予定と食い違うため。
- `PrivacyInfo.xcprivacy`（UserDefaults の利用理由 CA92.1 など）と記述を合わせる。設定のキーは
  `SaifuLog/App/AppSettings.swift` にまとめ、置き場所は `UserDefaults.standard`（アプリ専用の領域）だけにする
  （CA92.1 はアプリ自身だけが読み書きする使い方に限られる。App Group の共有の領域に置くなら理由 1C8F.1 を足す）。
  マニフェストに CA92.1 があることはアプリのテストで確かめる。

## 12. 競合と差別化

| アプリ | 入力の特徴 |
|---|---|
| トーク家計簿 | AI に話しかけて記録する |
| LINEで家計簿 | LINE のトークに「ランチ 800」と送って記録する |

他社の料金やデータの扱いは変わりうるため、ここでは比較の記号を付けず、入力の特徴だけを書く。

SaifuLog の差別化は次の 3 つ。

1. **端末内 AI で、データが外に出ない。** 開発者のサーバーを持たず、家計のデータを端末の外へ
   送らない（利用者が有効にした iCloud を除く）。
2. **自然な文章をそのまま理解する。** 割り勘・複数件・日付の言い回しを一行で書ける。
3. **買い切り。** サブスクにしない。

| 体験と端末の時計 | 体験の始まりは App Store の記録（再インストールでやり直せない）だが、今の時刻は端末の時計なので、時計を戻すと体験を延ばせる | 受け入れる（体験の後は買い切りで、時計を戻し続ける手間に見合わないため）。問題になったら、StoreKit の署名の日時（signedDate）を今の時刻の下限に使うことを考える（オフラインでは古いままなので、それだけでは防げない） |
| 購入のテスト | iOS 26.3・26.4 のシミュレータでは、xcodebuild test から SKTestSession を使えない（Apple の不具合） | 購入のテストは `make test-storekit` で iOS 26.2 のシミュレータで動かし、飛ばされたら失敗にする（CI も。ランナーにランタイムが無ければ入れる）。Xcode の Test では、使えないシミュレータなら飛ばす。購入の事実を差し替えるテストでも状態の決め方を守る。ランナーでランタイムを入れられなくなったら CI が止まるので、そのときは動く版を探して `STOREKIT_TEST_OS` を変える |
| プライバシー表示 | SDK を 1 つ入れるだけで「データの収集なし」が崩れる | 解析・広告の SDK を入れない |
| iCloud 導入時の移行 | 後からモデルを CloudKit の制約に合わせると、移行が要る | 最初から制約に合わせる（§5-2） |
| 共有の実現性 | SwiftData 単体では CloudKit の共有を扱えない可能性がある（要確認） | 家族との共有に着手する前に検証する |
| ロック中の保存先 | 保存先は NSFileProtectionComplete なので、ロック中は開けない | 保存先は最初の画面が出る時点で開き、ロック中なら解除を待って開き直す（落とさない）。ウィジェットや App Intents を足すときに保護クラスを見直す（§5-4） |
| 提出物のエンタイトルメント | 署名なしのアーカイブでは、データ保護などのエンタイトルメントが提出物から抜ける | release.yml は開発用の証明書で署名してアーカイブする。アップロードの前に `make export-ipa` で照合する（いまは警告だけ）。main で `mode=export` の照合が通るのを確かめてから、照合で止まるようにする（`docs/release-flow.md`） |
